# سنتــــر الأزهر | Al Azhar Center

متجر إلكتروني عربي لمركز الأزهر في شبين القناطر، يجمع بين كتالوج المنتجات والطلبات ولوحة إدارة المحتوى، مع واجهة واحدة تعمل على الويب وتطبيقات الهاتف والكمبيوتر.

> **مهم:** المشروع لا يضيف أسعارًا أو منتجات أو أرصدة مخزون افتراضية. صور المنتجات التي أرسلها صاحب المتجر موجودة في مكتبة الوسائط ليختارها المدير ويربطها ببيانات المنتج الحقيقية.

## نظرة عامة

المشروع يتكون من واجهة React تُبنى إلى ملفات ويب ثابتة، وخادم API مبني بـNestJS، وقاعدة SQLite للتطوير المحلي أو PostgreSQL عند ضبط `DATABASE_URL` للإنتاج. كل تطبيقات الويب والهاتف والكمبيوتر تتصل بالخادم نفسه، ولذلك تشترك في قاعدة بيانات واحدة.

- **واجهة المتجر:** `http://localhost:5173`
- **خادم API المحلي:** `http://127.0.0.1:3001`
- **فحص صحة API:** `http://127.0.0.1:3001/api/health`
- **قاعدة البيانات المحلية:** `.data/al-azhar-store.sqlite`
- **المتصفح:** يدعم التصفح والشراء من الشاشات الكبيرة والصغيرة.

لا يكفي رفع ملفات الواجهة الثابتة إلى GitHub Pages لتشغيل المتجر بالكامل؛ تسجيل الدخول والطلبات والإدارة تحتاج API حيًا وقاعدة بيانات دائمة. تعليمات الاستضافة موضحة أدناه.

## المزايا

### للزائر والعميل

- الصفحة الرئيسية والأقسام ومعلومات التواصل والخريطة.
- تصفح الأقسام والمنتجات والبحث والتصفية.
- سلة شراء محفوظة في المتصفح، والتحقق من السعر والمخزون على الخادم عند الطلب.
- الطلب كضيف أو بحساب، مع الدفع عند الاستلام أو Paymob عند اكتمال إعداداته.
- صفحة الحساب لتحديث البيانات والصورة الشخصية واللون وحجم الخط وكلمة المرور ومتابعة الطلبات.
- واجهة عربية RTL مع خيار اللغة الإنجليزية، ووضع فاتح/داكن وتفضيلات العرض.
- مساعد محادثة يرسل السؤال إلى مزود الذكاء الاصطناعي من الخادم، من دون مفتاح API في المتصفح.

### للمدير

- إنشاء المنتجات وتعديلها وإخفاؤها وإدارة الأسعار والمخزون والتصنيفات وبيانات SKU/الباركود.
- اختيار صور المنتجات من مكتبة الصور أو رفع وسائط جديدة.
- متابعة الطلبات وتحديث حالتها.
- إدارة حسابات العملاء، وإظهار نشاط الاتصال وآخر ظهور منفصلًا عن حالة تفعيل الحساب.
- تعديل النصوص والألوان والصور وروابط التواصل وإعدادات الشحن ومحتوى الصفحة الرئيسية.
- إضافة وتعديل وإخفاء وحذف أقسام وصور صفحة المركز.

### بيانات تجريبية وبيانات المتجر

عند تشغيل قاعدة بيانات جديدة، ينشئ الخادم جداول المتجر وبعض التصنيفات ومحتوى الصفحات الافتراضي. **لا ينشئ حساب مدير افتراضيًا ولا يضيف منتجات أو أسعارًا أو مخزونًا افتراضيًا.** يجب إدخال تفاصيل المنتجات والأسعار والمخزون الفعلية من لوحة الإدارة.

## صور المتجر

أُضيفت **34 صورة أصلية أرسلها صاحب المتجر** إلى `public/catalog/` بأسماء `customer-photo-01.png` إلى `customer-photo-34.png`. تتضمن صور الزي الأزهري والطاقيات والمصاحف والكتب والأرفف والإجازات والسبح والعطور ومستلزمات الصلاة.

تظهر هذه الصور تلقائيًا في مكتبة الصور داخل لوحة الإدارة (قسم المنتجات والوسائط). لعرض صورة كصورة منتج:

1. أضف المنتج أو افتح المنتج المطلوب من لوحة الإدارة.
2. أدخل الاسم والسعر والمخزون والتصنيف وبقية المعلومات المؤكدة.
3. اختر الصورة المناسبة من مكتبة الوسائط، ثم احفظ المنتج.

لم تُربط الصور تلقائيًا بأسماء أو أسعار أو منتجات محددة؛ بعض الصور ملصقات ترويجية تحتوي أرقام هواتف وعناوين، ولذلك يجب مراجعة الصورة واختيارها للقسم الصحيح قبل نشرها كصورة منتج.

## المتطلبات والتشغيل المحلي

### المتطلبات

- Node.js حديث يدعم `node:sqlite` (يفضّل Node.js 22 أو أحدث).
- npm.
- لا يحتاج التشغيل المحلي إلى قاعدة بيانات خارجية؛ SQLite تُدار من الخادم.
- عند ضبط `DATABASE_URL` يستخدم الخادم PostgreSQL بدل SQLite؛ لا تضع بيانات الاتصال في ملفات الواجهة أو GitHub.
- لا يلزم مفتاح AI أو Paymob لتشغيل الموقع؛ الميزات المرتبطة بهما لا تعمل حتى تُضبط مفاتيحهما.

### خطوات التشغيل على Windows

من PowerShell داخل مجلد المشروع:

```powershell
npm ci
Copy-Item .env.example .env
npm run dev
```

ثم افتح [http://localhost:5173](http://localhost:5173). يشغّل `npm run dev` خادم Vite وخادم NestJS معًا، ويُنشئ الخادم قاعدة البيانات عند أول تشغيل.

لإيقاف التشغيل، اضغط `Ctrl+C` في الطرفية. للتشغيل المنفصل:

```powershell
npm run dev:web
npm run dev:api
```

لضبط بيانات مدير المتجر بعد بدء API:

```powershell
npm run admin:setup
```

اتبع الأسئلة في الطرفية لإعداد حساب المدير؛ لا توجد كلمة مرور افتراضية. شغّل الأمر من نسخة الخادم التي تستخدم قاعدة البيانات الصحيحة.

### إعداد البيئة

انسخ `.env.example` إلى `.env` محليًا، ولا ترفع `.env` إلى GitHub. المتغيرات السرية تبقى على الخادم فقط.

| المتغير | مطلوب؟ | الاستخدام |
|---|---:|---|
| `PORT` | لا | منفذ API؛ الافتراضي `3001`. |
| `HOST` | للإنتاج | عنوان الاستماع؛ الافتراضي محليًا `127.0.0.1`. استخدم `0.0.0.0` خلف موازن/وكيل الاستضافة. |
| `NODE_ENV` | للإنتاج | استخدم `production` خلف HTTPS لتفعيل خصائص Cookie الإنتاجية. |
| `CORS_ORIGINS` | حسب الاستضافة | قائمة مصادر الويب المسموحة مفصولة بفواصل، مثل `https://store.example.com`. لا تضع مسارًا مثل `/api`. |
| `AZHAR_STORE_DB` | لا | مسار ملف SQLite؛ الافتراضي `.data/al-azhar-store.sqlite`. |
| `DATABASE_URL` | للإنتاج | رابط اتصال PostgreSQL؛ عند وجوده يتصل الخادم بقاعدة PostgreSQL بدل SQLite. خزّنه كمتغير سري على الخادم. |
| `AZHAR_STORE_UPLOAD_DIR` | للتوافق | مجلد قراءة الصور القديمة المحفوظة قبل تخزين الوسائط في قاعدة البيانات؛ الافتراضي `.data/site-content`. |
| `VITE_API_BASE_URL` | للتطبيقات والإنتاج | أصل API العام وقت بناء الواجهة، مثل `https://api.example.com`، **من دون** `/api` في النهاية. اتركه فارغًا للتطوير المحلي. |
| `CHATBOT_API_KEY` | اختياري | مفتاح مزود المحادثة من Google AI Studio. يبقى سرًا في بيئة الخادم. |
| `CHATBOT_API_URL` | اختياري | عنوان Chat Completions للمزود؛ القيمة الافتراضية موجودة في `.env.example`. |
| `CHATBOT_MODEL` | اختياري | اسم النموذج لدى المزود؛ القيمة الافتراضية مضبوطة في `.env.example`. |
| `PAYMOB_API_KEY` | للدفع الإلكتروني | مفتاح تاجر Paymob Accept. |
| `PAYMOB_INTEGRATION_ID` | للدفع الإلكتروني | رقم تكامل الدفع. |
| `PAYMOB_IFRAME_ID` | للدفع الإلكتروني | رقم صفحة/إطار الدفع. |
| `PAYMOB_HMAC_SECRET` | للدفع الإلكتروني | سر التحقق من إشعارات Paymob. |
| `PAYMOB_NOTIFICATION_URL` | للدفع الإلكتروني | رابط HTTPS العام إلى `/api/payments/paymob/webhook`. |
| `PAYMOB_RETURN_URL` | للدفع الإلكتروني | صفحة HTTPS العامة التي يعود إليها العميل بعد الدفع؛ مثل `/payment-result`. |

للتطبيقات المبنية على جهازك، عيّن أصل API قبل البناء:

```powershell
$env:VITE_API_BASE_URL = "https://api.example.com"
```

لا تضع `VITE_API_BASE_URL` في `.env` الخاص بالخادم وتتوقع أن ينتقل تلقائيًا إلى كل تطبيق؛ هذه القيمة تُضمّن في ملفات الواجهة وقت البناء. تغيير عنوان API يعني إعادة بناء التطبيقات.

## إدارة المتجر

### إنشاء أول مدير

```powershell
npm run admin:setup
```

لا توجد كلمة مرور افتراضية، ولا تنشئ قاعدة البيانات حساب مدير تلقائيًا. شاشة التسجيل العامة تنشئ حساب عميل فقط؛ إعداد المدير يتم بهذا الأمر من الطرفية.

يستخدم الأمر قاعدة البيانات التي يحددها `DATABASE_URL`:

- إذا لم يكن `DATABASE_URL` مضبوطًا، ينشئ المدير في SQLite المحلية `.data/al-azhar-store.sqlite`، ولن يصبح حسابًا على الموقع المنشور.
- لإعداد مدير على موقع الإنتاج، شغّل الأمر محليًا مع `DATABASE_URL` مضبوطًا مؤقتًا على رابط PostgreSQL الإنتاجي نفسه الموجود في **Vercel → Project → Settings → Environment Variables**. أدخل الاسم والبريد والهاتف وكلمة المرور عند الطلب، ثم أزل المتغير من بيئة الطرفية بعد انتهاء الأمر.
- لا تضع رابط قاعدة البيانات في Git أو متغير يبدأ بـ`VITE_`، ولا ترسله في المحادثات أو لقطات الشاشة. تأكد من استخدام قيمة **Production** لا قيمة **Preview**.
- إذا كان البريد غير موجود في قاعدة الإنتاج، ينشئ الأمر حساب مدير بكلمة المرور التي أدخلتها. إذا كان البريد موجودًا بالفعل، يرفع دوره إلى `ADMIN` ويحدّث الاسم والهاتف، لكنه **لا يغيّر كلمة المرور**؛ استخدم كلمة المرور المسجلة في قاعدة الإنتاج.

المعاينة المحلية مثل `http://localhost:5173` تستخدم قاعدة التطوير المحلية افتراضيًا، بينما `https://alazharcenterstore.vercel.app` يستخدم قاعدة PostgreSQL التي يشير إليها `DATABASE_URL` في Vercel. لذلك قد يعمل حساب المدير في المعاينة ولا يعمل على الإنتاج إلى أن يُنشأ أو يُرقّى في قاعدة الإنتاج نفسها.

### إدارة المنتجات والتصنيفات

- تُسجل تفاصيل المنتج في قاعدة البيانات: الاسم والوصف والتصنيف والسعر والمخزون والصورة والحالة، وحقول اختيارية مثل SKU والباركود والعلامة التجارية والوحدة.
- السعر والمخزون المعتمدان عند إنشاء الطلب هما الموجودان على الخادم، وليس ما أرسله المتصفح.
- التصنيف لا ينشئ منتجًا تلقائيًا.
- الصور الـ34 الجديدة متاحة في منتقي مكتبة صور المنتجات في لوحة الإدارة؛ اختيارها لا يملأ بيانات السعر أو المخزون.
- لا تُظهر المنتجات غير النشطة للشراء، ويُتحقق من الكميات المتاحة عند تسجيل الطلب.

### محتوى الموقع وإعداداته

لوحة الإدارة تسمح بتعديل أقسام الصفحة الرئيسية والمركز، نصوص الواجهة التسويقية، صور الأقسام، بيانات التواصل والخريطة، اللون، وروابط التواصل. يمكن إضافة أقسام وصور متعددة من إدارة المحتوى.

قيم الشحن الافتراضية عند إنشاء قاعدة بيانات جديدة هي `shipping_fee=35` و`free_shipping_threshold=500` بالجنيه المصري، ويمكن للمدير تغييرها من الإعدادات. هذه قيم إعداد ابتدائية وليست أسعار منتجات.

الصور الجديدة التي يرفعها المدير تُخزن داخل قاعدة البيانات وتُقدّم من `/api/media/:id`. يبقى المسار `/api/site-content/:fileName` لقراءة الصور القديمة الموجودة في `AZHAR_STORE_UPLOAD_DIR`.

تخدم واجهة API ملفات `public/` للوسائط العامة؛ لذلك تعمل روابط `/catalog/...` لصور العميل المختارة عند استخدام `VITE_API_BASE_URL`.

## الحسابات والأمان

- كلمات المرور تُجزّأ باستخدام `scrypt`.
- تسجيل الجلسة يستخدم Cookie باسم `azhar_session` بخصائص `HttpOnly`.
- قاعدة البيانات تحفظ بصمة رمز الجلسة فقط، وليس الرمز نفسه.
- تُحدّث حالة الاتصال أثناء استخدام الموقع، مع حفظ آخر ظهور؛ وحالة الحساب المفعّل/المعطّل منفصلة عن الاتصال.
- تعطيل حساب عميل يمنع تسجيل الدخول ويبطل جلساته. لا يمكن حذف حساب إدارة من شاشة العملاء.
- حذف حساب عميل يفصل طلباته السابقة عن الحساب بدل حذف سجل الطلبات.
- صور الحساب الشخصية وصور المنتجات المرفوعة محددة الصيغ والحجم، وتُخزن في قاعدة البيانات.
- في الإنتاج، يجب تشغيل الموقع وAPI عبر HTTPS وضبط CORS للمصادر المطلوبة فقط.
- لا تضع أسرارًا في الشيفرة أو مستودع Git أو متغيرات `VITE_*`؛ كل ما يبدأ بـ`VITE_` يصبح جزءًا من ملفات الواجهة العامة.
- مفاتيح chatbot وPaymob تُضبط على الخادم فقط. لا تشاركها في المحادثات أو لقطات الشاشة.

## الطلبات والدفع

### الدفع عند الاستلام

الدفع عند الاستلام متاح دون إعداد بوابة خارجية. يتحقق الخادم من المنتجات والكميات، يحسب الإجمالي ورسوم الشحن، ويحجز المخزون داخل معاملة قاعدة البيانات النشطة.

### Paymob Accept

يظهر خيار Paymob للعميل فقط عند اكتمال بياناته في بيئة API. تجهيز الدفع يتطلب حساب تاجر وتكامل فعالًا وعناوين HTTPS عامة.

1. ضع قيم Paymob الحقيقية في بيئة الخادم فقط، بحسب الأسماء في `.env.example`.
2. اضبط عنوان إشعارات Paymob على `https://<api-domain>/api/payments/paymob/webhook`.
3. اضبط عنوان الرجوع على صفحة المتجر العامة، مثل `https://<store-domain>/payment-result`.
4. اختبر على بيئة/مفاتيح الاختبار أولًا وتأكد من وصول إشعار HMAC والتحقق منه.
5. اختبر دورة ناجحة وفاشلة ومنتهية قبل تفعيل بيانات الإنتاج.

لا يخزن المتجر بيانات البطاقة؛ تتم عملية الدفع عبر Paymob. تنتهي الطلبات الإلكترونية غير المكتملة بعد ساعة ويُعاد المخزون، والإشعار المتأخر أو غير المطابق لا يُقبل كدفعة ناجحة تلقائيًا.

> لا توجد مفاتيح أو بيانات تاجر حقيقية مضمنة في المشروع؛ تكامل الإنتاج غير جاهز حتى يضبطه مالك حساب Paymob ويختبره.

## المساعد الذكي

تُرسل الرسائل إلى مزود متوافق مع OpenAI Chat Completions من الخادم، ويُستخدم كتالوج المنتجات الحالي وأسعارها ومخزونها كسياق للإجابة عن المتجر. لا توجد إجابات تجريبية احتياطية. إذا لم يكن المفتاح مضبوطًا أو تعذر المزود، يعرض التطبيق رسالة توضح المشكلة بدل اختلاق إجابة.

للتفعيل:

1. أنشئ مفتاحًا في Google AI Studio.
2. اضبط `CHATBOT_API_KEY` في بيئة خادم API.
3. راجع `CHATBOT_API_URL` و`CHATBOT_MODEL` إذا كنت تستخدم نموذجًا أو عنوانًا مختلفًا.
4. أعد تشغيل API واختبر سؤالًا عن منتج موجود فعلًا في قاعدة البيانات.

أخطاء توفر المزود أو حصته، ومنها `503`، مصدرها مزود الذكاء الاصطناعي ولا تعني وجود بيانات مخزون تجريبية في المتجر.

## تطبيقات Android والكمبيوتر

تشارك التطبيقات الواجهة نفسها، لكنها **تحتاج إلى API عام دائم عبر HTTPS** لتسجيل الدخول والمنتجات والطلبات. تطبيق الهاتف/الكمبيوتر ليس نسخة مستقلة من قاعدة البيانات ولا يضمّن ملف SQLite أو مفاتيح Paymob/AI داخله.

| المنصة | إطار العمل | صيغة الإخراج في سير العمل |
|---|---|---|
| Windows 64-bit x64 | Tauri | مثبت NSIS |
| Windows 32-bit x86 | Tauri | مثبت NSIS |
| Windows ARM64 | Tauri | مثبت NSIS |
| Linux x64 | Tauri | DEB وRPM |
| Android | Capacitor | APK إصدار غير موقّع تلقائيًا |

يُنتج سير العمل حزم Windows x64 وx86 وARM64، وحزم Linux x64 بصيغتي DEB وRPM، وAPK لأندرويد. لا يتضمن المشروع بناء تطبيقات macOS أو iOS. يتطلب توزيع Android على المتجر إعداد توقيع رسمي؛ APK الآلي غير موقّع، وحزم الكمبيوتر غير موقعة افتراضيًا.

## النشر والاستضافة

### نشر الواجهة وAPI على Vercel

يُشغّل المشروع API كـVercel Function واحدة في `api/index.ts`. تعيد قاعدة `rewrites` في `vercel.json` توجيه جميع مسارات `/api/*` إلى هذه الدالة، ثم يعيد المعالج بناء المسار الأصلي قبل تمريره إلى NestJS؛ وهذا يشمل المسارات المتداخلة مثل `/api/auth/login` و`/api/payments/options`. لا تحذف قاعدة إعادة الكتابة عند تعديل إعداد Vercel. Vercel يشغّل SQLite على مساحة مؤقتة؛ لذلك يجب استخدام PostgreSQL خارجية دائمة مثل Neon.

1. في Neon انسخ **pooled connection string** لقاعدة البيانات.
2. في Vercel افتح **Project → Settings → Environment Variables**، وأضف `DATABASE_URL` إلى بيئة Production باستخدام قاعدة Neon الإنتاجية. إذا كنت تستخدم معاينات Vercel، خصص لها قاعدة منفصلة في نطاق Preview ولا توجّهها إلى بيانات الإنتاج إلا عند الضرورة. لا تستخدم متغيرًا يبدأ بـ`VITE_` لهذا السر.
3. أعد نشر مشروع Vercel. تحقق من `https://al-azhar-center-store.vercel.app/api/health`؛ المتوقع `{"ok":true,"database":"connected"}`.
4. إعداد المشروع: Root Directory `./`، Framework Preset **Vite**، Install Command `npm ci`، Build Command `npm run build`، Output Directory `dist`.
5. لا تحتاج الواجهة على Vercel إلى `VITE_API_BASE_URL` لأن `/api/*` على النطاق نفسه. تطبيقات Windows وLinux وAndroid تستخدم نطاق Vercel كعنوان API افتراضي. غيّر Repository Variable الاختياري `VITE_API_BASE_URL` في GitHub Actions فقط إذا تغيّر النطاق؛ لا حاجة إلى وضعه كـSecret.

نطاق الموقع الحالي هو [https://alazharcenterstore.vercel.app](https://alazharcenterstore.vercel.app). بعد النشر، تحقق من المسارات التالية:

- `GET /api/health` يعيد `{"ok":true,"database":"connected"}`.
- `GET /api/auth/me` يعيد `{"user":null}` عند عدم وجود جلسة، وليس 404.
- `GET /api/payments/options` يعيد طرق الدفع المتاحة، وليس 404.

إذا ظهر `401` عند تسجيل الدخول، فقد وصل الطلب إلى API لكن بيانات الحساب أو كلمة المرور غير مطابقة لقاعدة البيانات التي يستخدمها ذلك النشر. إذا ظهر `404` من Vercel مع `X-Vercel-Error: NOT_FOUND`، فتحقق من نشر الدالة وقاعدة إعادة الكتابة للمسارات `/api/*`.

تُنشأ جداول PostgreSQL وإعدادات الموقع عند بدء أول Function. `npm run admin:setup` يستخدم قاعدة البيانات نفسها لإعداد المدير؛ شغّله محليًا مع `DATABASE_URL` مضبوطًا إلى قاعدة Neon. الصور المرفوعة تُخزن في جدول `media`. حد Vercel لطلب HTTP يفرض ألا يتجاوز حجم الصورة المرفوعة 3 ميجابايت. إعدادات `CHATBOT_API_KEY` وPaymob تُضاف إلى إعدادات بيئة Vercel على الخادم فقط عند تفعيلها.

تطبيقات Windows وLinux وAndroid تستخدم نطاق Vercel كعنوان API افتراضي. يمكن تغيير ذلك عبر Repository Variable اختياري باسم `VITE_API_BASE_URL` في GitHub Actions، من دون `/api` في النهاية؛ لا حاجة لإضافته كـSecret أيضًا.

> يجب أن يكون موقع الواجهة وAPI على HTTPS في الإنتاج لأن Cookies الجلسات الآمنة والدفع الإلكتروني يتطلبان اتصالًا مشفرًا. اختبر تسجيل الدخول وإنشاء طلب وعودة Paymob بعد ربط النطاق.

### ما لا يفعله GitHub Pages

GitHub Pages يستضيف ملفات ثابتة فقط، ولا يشغّل NestJS أو SQLite أو chatbot أو webhook للدفع. يمكن استضافة `dist/` عليه للواجهة، لكن يلزم API خارجي دائم وقيم CORS وعنوان API مناسب، كما أن الدفع يتطلب خادم webhook عام.

## النسخ الاحتياطي واستعادة البيانات

قاعدة البيانات تحفظ الحسابات والمنتجات والطلبات والإعدادات والمحتوى ووسائط الرفع. الصور الأصلية في `public/catalog/` ضمن المستودع. احتفظ بنسخة من:

- قاعدة البيانات المحددة بـ`DATABASE_URL` (أو ملف SQLite المحدد بـ`AZHAR_STORE_DB` محليًا).
- جدول `media` ضمن قاعدة البيانات.

استخدم النسخ الاحتياطية المدمجة لدى مزود PostgreSQL أو `pg_dump`، واختبر الاستعادة قبل اعتمادها. عند استخدام SQLite، لا تنسخ ملفًا حيًا مع تجاهل ملفات WAL/SHM؛ أوقف API أو استخدم أداة SQLite Backup.

| Tauri لا يبني على Windows | ثبّت Rust target المناسب وVisual Studio C++ Build Tools وWebView2، ثم راجع خرج `npx tauri info`. |
| Android لا يُبنى | ثبّت Android SDK وJava 21، ثم نفّذ `npm run mobile:sync` وأعد البناء من مجلد `android`. |
| GitHub Actions يتوقف قبل البناء | تحقق من وجود متغير Repository `VITE_API_BASE_URL` ومن صحة عنوان HTTPS. افتح سجل الوظيفة لمعرفة المنصة أو الاعتماد الناقص. |
| فشل فحص CodeQL في GitHub | فحوص CodeQL مستقلة عن نشر Vercel وبناء ملفات الإصدارات؛ افتح سجل وظيفة CodeQL الفاشلة في تبويب Actions لمعرفة اللغة أو الإعداد الذي يحتاج إلى معالجة. |

## المساهمة والتغييرات

- حافظ على عدم إدخال بيانات أو أسعار أو أرصدة مخزون غير مؤكدة.
- لا ترفع `.env` أو قاعدة بيانات حقيقية أو صور حسابات العملاء أو مفاتيح التوقيع.
- اختبر التغييرات بـ`npm run build` و`npm run test:api` قبل النشر.
- تغييرات واجهة الهاتف تتطلب `npm run mobile:sync` قبل اختبار التطبيق الأصلي.
- تحديث أصول الهوية يمكن توليده من شعار المتجر باستخدام `npm run mobile:assets`.

## الترخيص والبيانات

الصور والهوية التجارية ومحتوى المتجر مقدمة لصالح مركز الأزهر؛ لا تستخدمها خارج المشروع دون إذن مالكها. تُدار بيانات العملاء والطلبات في قاعدة بيانات المتجر، ويجب حماية الخادم والنسخ الاحتياطية وفق سياسة خصوصية المتجر.
